# 🎁 長時間タスクの投げっぱなしテンプレート100選

寝ている間・外出中でも安心して任せられるように、スコープ・完了条件・チェックポイントまで明示した指示文の型を100本まとめました。

**受け取り方**: 下のコードブロック右上のコピーボタンでコピーするか、このファイルをそのままダウンロードしてください。

**使い方**: `run_in_background: true`で実行するか、バックグラウンドで動かしたいタスクの冒頭にそのまま貼ってください。制限に達しても、オートコンティニュー チェックボックスがオンなら自動で続きから再開します。

```text
【カテゴリ1: リファクタリング系】

1. 前提: 大きめのモジュールを段階的に整理したい長時間タスク。
指示: src配下の対象モジュールを1ファイルずつ走査し、重複ロジックを共通関数に切り出して。既存のテストが通ることを1ファイル処理するごとに確認して。
出力形式: 変更ファイル一覧と差分サマリを最後にまとめて報告して。テストが落ちたファイルは元に戻して次に進んで。

2. 前提: 命名規則が統一されていない古いコードベースの整理。
指示: 命名規則ガイド（CLAUDE.md記載）に沿って、変数名・関数名を1ディレクトリずつ機械的にリネームして。呼び出し元の参照も漏れなく更新して。
出力形式: ディレクトリごとにリネーム件数を記録し、最後に合計件数の表で報告して。

3. 前提: 非推奨APIが複数箇所に残っているプロジェクトの移行。
指示: 非推奨APIの使用箇所を全部洗い出し、新APIへ1箇所ずつ置き換えて。置き換えごとに該当テストを実行して。
出力形式: 置き換え済み・要確認（自動判断できなかった）の2リストに分けて最後に報告して。

4. 前提: 型注釈が不足しているコードベースの型安全性向上。
指示: 型チェッカーの警告が出ているファイルを優先度順に処理し、型注釈を追加して。any型は理由がなければ具体型に置き換えて。
出力形式: 処理前後の警告件数の推移を、10ファイル処理するごとに記録して最後に一覧で出して。

5. 前提: 依存が循環しているモジュール構成の整理。
指示: 循環依存を検出し、依存の向きが一方向になるよう段階的に構造を整理して。1回の変更ごとにビルドが通るか確認して。
出力形式: 循環が解消された箇所と、手動判断が必要で保留した箇所を分けて報告して。

6. 前提: 巨大な関数・クラスの分割によるメンテナンス性向上。
指示: 100行を超える関数を優先度順にリストアップし、責務ごとに小さな関数へ分割して。分割後も既存の呼び出し側の挙動が変わらないことを確認して。
出力形式: 分割前後の行数と、分割した関数名の対応表を最後にまとめて。

7. 前提: 古いフレームワークバージョンの書き方が混在するコード整理。
指示: 旧記法を新記法へ1ファイルずつ統一して。移行ガイド（プロジェクト内docs）に記載のパターンだけを機械的に置き換えて。
出力形式: 置き換えたパターンの種類ごとに件数を集計し、最後に表で報告して。

8. 前提: エラーハンドリングの書き方がバラバラなプロジェクトの統一。
指示: try/catchの書き方を、プロジェクト標準のエラーハンドリングパターンに1モジュールずつ揃えて。ログ出力の形式も統一して。
出力形式: 統一したファイル数と、パターンから外れていて判断に迷った箇所のリストを最後に出して。

9. 前提: コメントアウトされた古いコードの整理。
指示: コメントアウトされたコードブロックを1ファイルずつ確認し、明らかに不要なものは削除、判断が難しいものは要確認リストへ。
指示: git履歴で最終更新が1年以上前のものを優先して処理して。
出力形式: 削除件数と要確認リストを最後にまとめて報告して。

10. 前提: パッケージのバージョン固定・整理。
指示: package.json（または相当ファイル）の依存関係を1つずつ確認し、メジャーバージョンが古いものをリストアップして。破壊的変更の有無をリリースノートで確認して。
出力形式: 更新可能・要注意（破壊的変更あり）の2リストに分けて最後に報告して。

【カテゴリ2: テスト整備系】

11. 前提: テストカバレッジが低いモジュールの底上げ。
指示: カバレッジレポートを元に、カバレッジが低いファイルから優先的にユニットテストを追加して。1ファイル追加するごとにカバレッジ率を記録して。
出力形式: 処理前後のカバレッジ率の推移表を最後に出して。

12. 前提: 壊れているテスト（flaky test）の調査と修正。
指示: CIで不安定に失敗しているテストを1つずつ実行し、原因（タイミング依存・外部依存等）を特定して修正して。
出力形式: 修正したテスト名と原因の対応表を最後にまとめて報告して。

13. 前提: 統合テストが不足している主要フローの補完。
指示: ユーザーの主要な操作フロー（ログイン・決済等、CLAUDE.md記載）を1つずつ洗い出し、統合テストを追加して。
出力形式: 追加したテストのフロー名一覧を最後に報告して。

14. 前提: スナップショットテストの陳腐化した内容の整理。
指示: 既存のスナップショットテストを1ファイルずつ確認し、実際の出力と乖離が大きいものを更新して。意図的な変更か不具合かを判断して。
出力形式: 更新したスナップショットと、不具合の疑いがあるため保留した箇所を分けて報告して。

15. 前提: テストの実行時間が長くなっているスイートの高速化。
指示: 実行時間が長いテストを1つずつプロファイリングし、不要な待機やセットアップを削減して。
出力形式: テストごとの実行時間の変化（改善前後）を最後に表で報告して。

16. 前提: モックの使い方が古いテストコードの現代化。
指示: 古いモックライブラリの記法を、現在の標準的な書き方へ1ファイルずつ書き換えて。挙動が変わらないことをテスト実行で確認して。
出力形式: 書き換えたファイル数と、書き換え中に見つかった不審な挙動のメモを最後に報告して。

17. 前提: E2Eテストのシナリオ追加。
指示: 主要な画面遷移パターンを1つずつ洗い出し、E2Eテストシナリオとして追加して。既存シナリオと重複しないか確認して。
出力形式: 追加したシナリオ数と、カバーできた画面遷移の一覧を最後に報告して。

18. 前提: エッジケースのテスト漏れ調査。
指示: 主要な関数について、境界値・異常系のテストが漏れていないか1つずつ確認し、不足分を追加して。
出力形式: 追加したエッジケーステストの件数と対象関数の一覧を最後にまとめて。

19. 前提: テストデータ（フィクスチャ）の整理と共通化。
指示: 各テストファイルに散らばっている重複したテストデータを1つずつ確認し、共通のフィクスチャファイルへ集約して。
出力形式: 集約したフィクスチャの一覧と、削減できた重複行数を最後に報告して。

20. 前提: リグレッションテストの自動化整備。
指示: 過去のバグ修正履歴（git履歴・issue）から再発しやすい箇所を洗い出し、それぞれにリグレッションテストを追加して。
出力形式: 追加したテストと対応する過去バグの対応表を最後に報告して。

【カテゴリ3: ドキュメント整備系】

21. 前提: READMEやdocsが古いままのプロジェクトの更新。
指示: 現在のコードの挙動と既存ドキュメントを1セクションずつ突き合わせ、乖離している箇所を実際の挙動に合わせて更新して。
出力形式: 更新したセクション一覧と、判断に迷って手つかずのまま残した箇所を最後に報告して。

22. 前提: API仕様書がコードと同期していない状態の解消。
指示: 実装済みのAPIエンドポイントを1つずつ確認し、仕様書に記載のリクエスト・レスポンス形式を実装に合わせて更新して。
出力形式: 更新したエンドポイント数と、実装と仕様書が大きく食い違っていた箇所のリストを最後に出して。

23. 前提: 関数・クラスのdocstring不足の解消。
指示: 公開関数・クラスのうちdocstringが無いものを1つずつリストアップし、引数・戻り値・簡単な使用例を追記して。
出力形式: 追記した件数と対象ファイル一覧を最後にまとめて報告して。

24. 前提: セットアップ手順書の実機検証と更新。
指示: 既存のセットアップ手順を1ステップずつ実際に実行し、うまくいかない箇所を見つけたら手順を修正して。
出力形式: 検証した手順の結果（成功・修正あり）を最後に一覧で報告して。

25. 前提: 変更履歴（CHANGELOG）の整備。
指示: 直近のコミット履歴を確認し、まだCHANGELOGに反映されていない変更を種類別（機能追加・修正・破壊的変更）に整理して追記して。
出力形式: 追記した項目数を種類別に集計して最後に報告して。

26. 前提: アーキテクチャ図と実際の構成のズレの解消。
指示: 既存のアーキテクチャ図・構成説明と実際のディレクトリ構成・依存関係を突き合わせ、ズレている箇所をテキストで指摘して。
出力形式: ズレ箇所の一覧と、修正が必要な図の該当部分を最後にまとめて報告して。

27. 前提: 用語集（Glossary）の整備。
指示: コードベース内で使われているドメイン固有の用語を1つずつ拾い出し、簡潔な説明つきの用語集としてまとめて。
出力形式: 収集した用語数と、説明文が確定できず要確認とした用語のリストを最後に報告して。

28. 前提: トラブルシューティングガイドの拡充。
指示: 過去のissue・サポート記録から頻出するエラーを1つずつ洗い出し、原因と対処法をトラブルシューティングガイドに追記して。
出力形式: 追記した項目数と対象エラーの一覧を最後にまとめて。

29. 前提: コードコメントの品質底上げ。
指示: 「なぜそうするか」が書かれていない意図不明なコメントを1ファイルずつ確認し、コード自体から意図を推測して補足して。
出力形式: 補足したコメント数と、意図が推測できず要確認とした箇所のリストを最後に報告して。

30. 前提: 移行ガイド・アップグレードガイドの作成。
指示: 過去の破壊的変更を1つずつ洗い出し、旧バージョンから新バージョンへの移行手順としてまとめて。
出力形式: まとめた移行項目数と、対応する変更のコミットハッシュ一覧を最後に報告して。

【カテゴリ4: 依存関係・アップデート系】

31. 前提: 使われていない依存パッケージの整理。
指示: package.json（または相当ファイル）に記載の依存を1つずつ確認し、実際にコード内で使われているかを検索して確認して。
出力形式: 未使用と判定した依存の一覧と、削除の可否を最後に報告して（削除は実行せず提案のみ）。

32. 前提: 脆弱性のある依存パッケージの棚卸し。
指示: 依存パッケージの脆弱性情報を1つずつ確認し、アップデートで解消できるものと、破壊的変更を伴うものを分類して。
出力形式: 即時アップデート可能・要検討の2リストに分けて最後に報告して（アップデート自体は実行しない）。

33. 前提: ライセンス互換性の確認。
指示: 依存パッケージのライセンスを1つずつ確認し、プロジェクトのライセンス方針（CLAUDE.md記載）と矛盾しないか確認して。
出力形式: 問題なし・要確認の2リストに分けて最後に報告して。

34. 前提: 型定義ファイル（型スタブ）の不足解消。
指示: 型定義が無いためanyになっている外部パッケージを1つずつ確認し、公式の型定義があれば導入を提案して。
出力形式: 型定義ありで導入可能・型定義なしで自作が必要、の2リストに分けて最後に報告して。

35. 前提: モノレポ内のパッケージ間バージョン不整合の解消。
指示: モノレポ内の各パッケージが参照する共通依存のバージョンを1つずつ確認し、不整合な箇所をリストアップして。
出力形式: 不整合が見つかったパッケージの組み合わせと、それぞれのバージョン差分を最後に報告して。

36. 前提: ビルド設定ファイルの重複・肥大化の整理。
指示: 複数存在するビルド設定の共通部分を1つずつ見つけ、共通設定ファイルへ抽出できないか整理して。
出力形式: 抽出できた共通設定の項目数と、抽出後の各設定ファイルの行数変化を最後に報告して。

37. 前提: 環境変数の一覧化と説明の整備。
指示: コード内で参照されている環境変数を1つずつ検索して洗い出し、用途と必須・任意の別を一覧表にまとめて。
出力形式: 洗い出した環境変数の一覧表を最後に出して。

38. 前提: CI設定ファイルの重複ジョブの整理。
指示: CI設定内の似た処理を行うジョブを1つずつ確認し、共通化できる箇所を整理して。
出力形式: 統合できたジョブ数と、CI実行時間の変化見込みを最後に報告して。

39. 前提: Dockerイメージのビルド時間短縮。
指示: Dockerfileのレイヤーを1つずつ確認し、キャッシュが効きやすい順序への並び替えを提案して。
出力形式: 並び替え案と、想定されるビルド時間の改善ポイントを最後に報告して。

40. 前提: 設定ファイルのスキーマ検証追加。
指示: 手書きの設定ファイル（JSON/YAML等）に対して、スキーマ検証を1ファイルずつ追加して。
出力形式: 検証を追加したファイル一覧と、検証で見つかった既存の不正値を最後に報告して。

【カテゴリ5: バグ調査・修正系】

41. 前提: 再現条件が不明瞭な不具合報告の切り分け。
指示: issueに記載された不具合を、関連しそうなコード箇所から1つずつ仮説を立てて検証して。再現条件を特定して。
出力形式: 特定できた再現条件と、まだ切り分けできていない仮説の一覧を最後に報告して（修正は次のタスクに回す）。

42. 前提: ログに残るエラーメッセージの原因調査。
指示: 直近のエラーログを種類別に分類し、頻出しているものから1つずつ原因コードを特定して。
出力形式: エラー種別ごとの発生件数と特定できた原因の対応表を最後に報告して。

43. 前提: パフォーマンス劣化が疑われる箇所の調査。
指示: 処理時間が長いと報告された機能を1つずつプロファイリングし、ボトルネックになっている箇所を特定して。
出力形式: 機能ごとのボトルネック箇所と、想定される改善方針を最後に報告して（修正は実行しない）。

44. 前提: メモリリークの疑いがある長時間稼働プロセスの調査。
指示: メモリ使用量が時間経過で増え続けている箇所を1つずつ確認し、解放されていないリソースを特定して。
出力形式: 特定した原因箇所と、対応が必要な優先度を最後に報告して。

45. 前提: 特定条件でのみ発生する競合状態（レースコンディション）の調査。
指示: 非同期処理が絡む箇所を1つずつ確認し、タイミング次第で結果が変わりうる箇所を特定して。
出力形式: 競合状態の疑いがある箇所の一覧と、それぞれの発生条件の推測を最後に報告して。

46. 前提: 文字化け・エンコーディング不具合の調査。
指示: 文字化けが報告されている処理経路を1つずつたどり、エンコーディングが変換される箇所を特定して。
出力形式: 特定した変換箇所の一覧と、原因と考えられる設定の不一致を最後に報告して。

47. 前提: タイムゾーン起因の日時ずれの調査。
指示: 日時を扱う処理を1つずつ確認し、タイムゾーンの扱いが統一されていない箇所を特定して。
出力形式: 特定した箇所の一覧と、統一すべきタイムゾーンの方針案を最後に報告して。

48. 前提: 権限・アクセス制御の不具合調査。
指示: アクセス制御のロジックを1機能ずつ確認し、意図しない権限で操作できてしまう箇所がないか調べて。
出力形式: 見つかった問題箇所の一覧と、深刻度の目安を最後に報告して。

49. 前提: 外部API連携のエラーハンドリング漏れ調査。
指示: 外部APIを呼び出している箇所を1つずつ確認し、エラーレスポンスやタイムアウトへの対処が漏れていないか調べて。
出力形式: 対処が漏れている箇所の一覧と、想定されるリスクを最後に報告して。

50. 前提: 大量データ処理時のみ発生する不具合の調査。
指示: 少量データでは再現しない不具合について、処理ロジックを1つずつ確認し、大量データ特有の原因を特定して。
出力形式: 特定した原因と、再現に必要なデータ規模の目安を最後に報告して。

【カテゴリ6: データ処理・移行系】

51. 前提: 古いデータ形式から新形式への段階的な変換。
指示: 対象データを一定件数ずつバッチで処理し、新形式への変換ルール（CLAUDE.md記載）に沿って変換して。
出力形式: バッチごとの処理件数・エラー件数を記録し、最後に合計を報告して。

52. 前提: 重複データの検出と統合案の作成。
指示: 対象テーブル・ファイルの重複しているとみられるレコードを1件ずつ照合し、統合候補をリストアップして。
出力形式: 統合候補の一覧と、判断基準（何をもって重複とみなしたか）を最後に報告して（統合は実行しない）。

53. 前提: データ整合性チェックの実施。
指示: 関連テーブル間の参照整合性を1テーブルずつ確認し、不整合なレコードを特定して。
出力形式: 不整合の件数と種類ごとの内訳を最後に報告して。

54. 前提: CSVやログファイルからの情報抽出・集計。
指示: 対象ファイル群を1つずつ読み込み、指定した項目（CLAUDE.md記載の集計方針）で集計して。
出力形式: 集計結果を種類別の表にまとめて最後に報告して。

55. 前提: 個人情報・機密情報のマスキング対象調査。
指示: データストア内のフィールドを1つずつ確認し、マスキングが必要そうな項目をリストアップして。
出力形式: マスキング候補フィールドの一覧と、判断理由を最後に報告して（マスキング処理は実行しない）。
```
